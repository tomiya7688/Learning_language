# 将来対応予定

このファイルは、まだ1つのIssueへ分解する段階ではない大きな構想や、将来対応したい方向性をまとめるための場所です。

Issueは原則として **1実装単位** で管理します。

そのため、

- 1つのIssueでは大きすぎるもの
- まだ実装順や分割方法が決まっていないもの
- 複数のIssueへ分割する前提の長期構想
- 将来追加したい言語・教材系列
- プロジェクト全体に関わる大きな方針

は、まずこのファイルへ置きます。

実装できる大きさまで内容が固まったら、このファイルから個別Issueへ切り出します。

### 対応優先順位

将来対応する言語は、基本的に次の順で優先します。

1. **高校生が情報の授業で使う言語**
2. **書ける人は少ないが、需要があり「書きたい」と思う人が多い言語**
3. **Tomiyaの言語**
4. **一般的な言語**
5. **現在の学習・実用需要がかなり限定的で、他の候補より後に扱う言語**

「Bend」は **5** として扱います。Bendはレガシー言語ではなく、現在も開発が続いている並列処理向けの高級言語です。一方で、現時点では利用者・教材需要ともかなり限定的で、仕様や処理系も動き続けているため、Learning_languageでは他の候補を先に教材化します。普及状況が変われば優先度は見直します。

「Squirrel」は **5** として扱います。ゲーム等への組み込みを意識した軽量スクリプト言語で、現在でも動かして学べる価値があります。一方で、現時点では新規にSquirrelを学ぶ必要がある場面や教材需要はかなり限定的なため、Luaなど他のスクリプト言語教材を優先したあとに扱います。

現時点では、**Simula、Smalltalk、ActionScript、Bend、Squirrel** を優先度5として扱います。

HaskellやCommon Lispは利用者が多い言語ではありませんが、現在も処理系の開発・更新が続いており、単なる歴史教材ではありません。COBOL・Fortran・Assembly系・Verilog HDL・LibreOffice Basicなども、実務・研究・既存資産・特定用途で学ぶ理由があるため5には下げません。

優先度5は「古い言語」という意味ではありません。**現在の学習・実用需要がかなり限定的で、他の候補を先に扱う方がよい場合**に使います。歴史・研究・既存資産が主目的の言語だけでなく、Bendのような新しく現役でも、まだ利用者や教材需要が小さい言語もここに含めます。
「Fortran」も **2** として扱います。数値計算・シミュレーション・HPCなどで既存コードに触れる研究者や修士課程の学生には、今でも「必要になったので学びたい」という需要があると考えます。一般的な入門教材が豊富な言語よりも、研究用途へ入るための分かりやすい教材を優先して用意する価値があります。

理由のひとつは、日本人がプログラミングへ入るときの最初の参入障壁になりやすいのが **英語** だからです。

英語の命令や変数名を読むこと自体が負担になる人にとって、日本語で書ける言語はプログラミングへ入る大きな入口になります。

ただし、なでしこを「最初にプログラミングを体験するためだけの言語」として扱うわけではありません。

Pythonと同じように、基礎から先まで継続して学べる教材を用意する方針です。

将来的には、少なくとも次の系列を用意します。

- 基礎編
- 応用文法編
- ゲーム編
- デスクトップアプリ編
- Webアプリ編
- 機械学習編

必要に応じて、これらも「ゆっくり学ぶ」「完成品から学ぶ」など複数の学び方へ分けます。

なでしこプロジェクトを応援する意味も含め、一般的な言語群より優先して教材化を検討します。

候補一覧の並び順そのものは、実装優先順位を表しません。

複数の分類に当てはまる場合は、より上の優先順位を採用します。
具体的な教材化の順番は、その時点の教材需要や準備状況も見ながら決めます。

## RPG (IBM i) 教材メモ

RPGは、歴史上の言語としてだけ扱うのではなく、**現在のIBM iで使われている言語**として教材化を検討します。

新しく学ぶ入口では、昔の固定形式から始めず、まず **RPG IV / ILE RPG の完全自由形式（fully free-form）** を中心にします。

教材化する場合の流れの候補:

1. IBM i と RPG が何なのか
2. RPGをどこに書いて、どうコンパイル・実行するのか
3. fully free-form RPGで最初のプログラムを書く
4. 変数、条件分岐、繰り返し、手続きなどを学ぶ
5. IBM i上のファイルやデータを扱う
6. 既存資産を読むために、固定形式RPGにも触れる

重要なのは、

> 古い固定形式を読めるようになること

だけをゴールにせず、

> 現代のRPGで新しくコードを書けるようになること

を先にすることです。

一方で、RPGはPythonのようにWindowsへ入れてすぐ動かす言語ではなく、主な実行環境がIBM iです。

そのため教材化では、**学習用のIBM i環境をどう用意するか** が最初の大きな課題になります。

## 言語に対する先入観を持ち込まない

このプロジェクトでは、

> 「この言語は○○専用」

という世間の先入観を、そのまま教材へ持ち込まないようにします。

たとえば、MicroPythonはRaspberry Pi専用の言語ではありません。

Raspberry Pi Picoなどで使われることはありますが、MicroPython自体はマイコンなどの小さな環境でPythonを使うための実装です。

同様に、

- Arduino = 教育用ボードだけのお遊び
- COBOL = 古いだけの言語
- Lisp = 研究者だけの言語
- Assembly = 全部を手書きするための言語

といった固定観念だけで教材の用途を決めません。

教材では、

- 何ができるのか
- どんな環境で使えるのか
- どんな場面で役に立つのか

を実際の用途から説明します。

## 設計思想編

Python応用編の中で、プログラムの組み立て方・考え方そのものを試す系列です。

最初の教材としてオブジェクト指向編を置きます。

将来候補として、

- 関数型の考え方
- 手続き型の考え方
- データ指向
- イベント駆動
- 宣言的な書き方

なども扱えますが、最初から全てを実装予定として固定はしません。

各系列は「これが正しい」と教えるのではなく、Pythonで実際に書いて違いを見る教材にします。

### オブジェクト指向編

この系列は、

> **オブジェクト指向ってよく聞くけど、なに？**

くらいのところから始めます。

最初から、

> オブジェクト指向で書くべき
>
> オブジェクト指向の方がよい
>
> これが正しい設計

という前提にはしません。

まず普通に小さなGUIアプリを作り、そのあとで、

> こういう考え方で組み立てる方法もある。やってみよう。

という形で、Pythonを使って実際に書き換えてみます。

書き換えた結果、

- コードのまとまり方がどう変わったか
- 状態を持つ場所がどう変わったか
- 処理を呼ぶ場所がどう変わったか
- クラス同士の関係がどう見えるようになったか

を観察します。

そのうえで、

> **こういう考え方をオブジェクト指向と呼んできた流れがあるんだよ**

というところまで説明します。

オブジェクト指向を採用するかどうかの評価は、教材側では下しません。

### 作るもの

1つのGUIアプリを少しずつ大きくしていきます。

候補としては、タスク管理・メモ管理など、

- 複数のデータを持つ
- 追加・編集・削除がある
- 画面の状態が変わる
- 保存 / 読み込みがある
- 複数の処理やデータのまとまりが見えてくる

題材を使います。

具体的な完成アプリは、実装をIssueへ切り出す段階で決めます。

### 最初はオブジェクト指向にしない

最初のGUIアプリは、必ずしも最初からオブジェクト指向で書きません。

まず動くものを作り、

> この値とこの処理は同じものとして扱えそう
>
> この処理は別のものへ任せる書き方もできそう
>
> この状態を外から直接触らず、そのものへ頼む形にもできそう

という箇所が出てきたところで、クラスやオブジェクトを使う書き方へ変えてみます。

ここで、

> 変更前は間違い
>
> 変更後が正解

とはしません。

**同じGUIアプリを別の考え方で書くと、コードがどう変わるのかを見る**教材にします。

### 扱う候補

- オブジェクトとは何か
- クラスとインスタンス
- `__init__` とインスタンス変数
- 状態と処理を同じクラスへ置く書き方
- 1つのクラスに何を持たせるか
- 処理を別のオブジェクトへ任せる書き方
- オブジェクト同士の関係
- オブジェクトを別のオブジェクトが持つ
- コンポジション
- カプセル化
- 公開する処理と内部だけで使う処理
- 継承
- オーバーライド
- ポリモーフィズム
- GUIとアプリ本体の処理を分ける書き方
- ファイル保存などの処理を別クラスへ分ける書き方
- 大きくなったクラスを分割する書き方
- クラス同士の依存関係
- テストしやすい構造との関係

これらを「オブジェクト指向なら必ずこうする」という規則としては扱いません。

実際に書いてみて、

> こういう分け方が提案されてきた
>
> こういう書き方も広く使われてきた

という形で見ていきます。

### クラスとオブジェクト指向を同一視しない

クラスはオブジェクト指向そのものではありません。

クラス、インスタンス、継承、メッセージ送信、カプセル化、コンポジションなどは、
それぞれ別の時期・別の文脈で提案され、後のオブジェクト指向の考え方へ取り込まれてきたものとして扱います。

したがって、

> classを書いたからオブジェクト指向

とも、

> 継承を使ったからオブジェクト指向

とも説明しません。

### 歴史は各要素の場所で説明する

歴史だけを独立した章でまとめて終わりにはしません。

各要素を説明する場所で、

> こういう問題に対して、こういう仕組みや考え方が提案された
>
> ↓
>
> こういう形で使われるようになった
>
> ↓
>
> その後、別の書き方も増えていった
>
> ↓
>
> 現代のPythonでは、このような書き方をよく見る

という流れを添えます。

「昔は間違っていた」「現代が正しい」という評価にはしません。

### クラスを説明するとき

Simulaでは、シミュレーション対象を表現するために、

- クラス
- インスタンス
- 状態を持つ対象
- 継承

などの仕組みが使われました。

これらは、その後のオブジェクト指向言語やオブジェクト指向設計へ取り込まれていきました。

教材では、

> Simulaがオブジェクト指向だったからクラスが生まれた

とは説明しません。

> **Simulaで使われたクラスやインスタンスなどの仕組みが、後のオブジェクト指向へ取り込まれていった**

という流れで扱います。

### オブジェクト同士の操作を説明するとき

Smalltalkでは、

- オブジェクトが状態を持つ
- オブジェクト自身が処理を持つ
- 他のオブジェクトへメッセージを送り、処理を依頼する

という見方が強く打ち出されました。

ここでは、

> データを外側から直接操作する

書き方とは別に、

> その操作を担当するオブジェクトへ頼む

という考え方が提案されたことを説明します。

**Smalltalkのコードは書きません。**

Smalltalkは歴史的背景と考え方の説明だけに使い、
実際のコード例はすべてPythonで書きます。

たとえば、

```python
task.complete()
window.show()
repository.save(task)
```

のようなPythonコードを使い、

> どの処理を、どのオブジェクトへ頼む形になっているか

を確認します。

### 継承を説明するとき

継承は、共通部分を引き継ぐ仕組みとして広く使われるようになりました。

その後、

- 深い継承階層を持つ設計
- 継承を多用しない設計
- 必要なオブジェクトを組み合わせるコンポジション

など、さまざまな書き方が使われるようになりました。

教材では、

> 継承は悪い
>
> コンポジションが正しい

とは評価しません。

同じGUIアプリを、

- 継承を使った場合
- オブジェクトを組み合わせた場合

で書いてみて、

> 何がどこへ置かれるのか
>
> どこから処理を呼ぶのか
>
> 変更するときにどこを見ることになるのか

を比較します。

### 現代のPython

Pythonでは、

- クラス
- 関数
- モジュール
- データ構造
- 継承
- コンポジション

を組み合わせて書けます。

そのため、

> 何でもクラスにするのがオブジェクト指向
>
> オブジェクト指向で書けばよい

とは教えません。

教材では、

> 現代のPythonでは、このような書き方をよく見る

と事実として紹介し、必要なら別の書き方も並べます。

### 教材の進め方

大まかには、

1. まずGUIアプリを作る
2. コードが増えてくる
3. 「この値と処理は同じものに見える」という箇所を探す
4. クラスを使う書き方へ変えてみる
5. オブジェクトへ処理を任せる書き方も試す
6. 継承を使う書き方も試す
7. コンポジションを使う書き方も試す
8. それぞれでコードがどう変わるかを見る
9. その要素が歴史上どのように提案・利用されてきたかを確認する
10. 現代のPythonでよく見る形も確認する

という流れにします。

最終的な目的は、

> オブジェクト指向が正しいと納得する

ことではありません。

> **オブジェクト指向という言葉で何が語られてきたのかを、Pythonで実際に試して理解する**

ことを目的にします。


## 文法・書き方編

基礎編で学んだ文法や標準機能を組み合わせて、

> **こういう書き方もできる**

を増やす系列です。

上級編の解析・デバッグほど重い内容ではなく、
基礎編を終えたあとにPythonの書き方の幅を増やす応用教材として扱います。

最初の候補として **小技・イディオム編** を用意します。

たとえば、

```python
def get_category(age):
    categories = {
        "Child": age < 13,
        "Teenager": 13 <= age < 18,
        "Adult": 18 <= age < 65,
        "Senior": age >= 65,
    }

    return next(name for name, matched in categories.items() if matched)
```

のようなコードを題材に、

- 連鎖比較
- 辞書
- `.items()`
- generator式
- `next()`

を組み合わせると、`if / elif` とは別の表現もできることを確認します。

ただし、

> if文はもう使わない
>
> この書き方の方がPythonらしくて正しい

とは教えません。

普通の `if / elif` 版も並べ、

- 何が短くなるか
- 何を知っていないと読みにくいか
- すべての条件式が辞書作成時に評価されること
- `next()` は一致しなければ例外になること
- 辞書の順序に意味を持たせていること

など、書き方を変えたときの性質の違いも扱います。

今後の候補:

- `enumerate()`
- `zip()`
- unpacking
- generator式
- `any()` / `all()`
- `next()`
- `min()` / `max()` の `key=`
- `sorted(..., key=...)`
- 辞書・集合内包表記
- `collections`
- `itertools`
- `dataclasses`
- `pathlib`
- context manager
- `getattr()` / `setattr()`
- `match`
- sentinel
- truthy / falsyを利用した書き方

教材では、

1. まず普通に書く
2. 別の書き方を見る
3. 何を組み合わせているか分解する
4. 実際に動かす
5. 挙動の違いを見る
6. 似た処理を書き換えてみる

という流れを基本にします。

## Python上級編

基礎編・応用編とは別に、**上級編**を用意します。

上級編は、

> 基礎編を終えたから次にやる

という位置付けにはしません。

Pythonである程度まとまったコードを書き、既存コードを読んだ経験もある人が、
さらに深く調査・解析・問題解決へ進みたいときに選ぶ系列とします。

構成候補:

```text
上級編/
├─ 解析・デバッグ編/
│  └─ 既知のPythonバグ解決編/
├─ 環境・依存関係編/
│  ├─ バージョン依存関係解決編/
│  ├─ パッケージング競合解決編/
│  └─ 依存関係がインストールされない問題解決編/
└─ 問題演習・ノック編/
   ├─ 穴埋めノック/
   ├─ 機能実装ノック/
   └─ 標準入出力ノック/
```

### 既知のPythonバグ解決編

実在し、すでに原因や修正方法が判明しているバグを題材にします。

基本の流れは、

1. バグを再現する
2. 現象を整理する
3. 最小再現コードを作る
4. テストで再現を固定する
5. 原因候補を絞る
6. 必要なら標準ライブラリやCPython実装まで追う
7. 自分で修正案を考える
8. テストを通す
9. 最後に実際の修正と比較する

とします。

「答えが分かっている問題」を解くのではなく、
**答えを最後まで隠した状態で、実際のデバッグ・調査手順を経験する**教材にします。

### バージョン依存関係解決編

Pythonの実運用でよく遭遇する、パッケージ同士のバージョン依存CONFLICTを意図的に再現して解消します。

たとえば、

```text
パッケージA → numpy < 2
パッケージB → numpy >= 2
```

のような、NumPy 1.x系と2.x系を同じ環境で別々に要求される状況を題材にします。

ここでは、

- 直接依存と間接依存
- バージョン指定
- dependency resolver
- requirements.txt
- pyproject.toml
- 仮想環境
- pin / lock
- 依存関係ツリー
- pipのCONFLICTメッセージ

などを扱います。

重要なのは、エラーが出たら手当たり次第にバージョンを変えることではなく、

> どの要求とどの要求が衝突しているのか

を追えるようにすることです。

共通して満たせるバージョン範囲が存在しない場合は、
同じPython環境ではその依存条件を同時に成立させられないことも扱います。

そのうえで、

- 依存元を更新する
- 互換バージョンへ戻す
- バージョンを固定する
- ライブラリを置き換える
- fork / patchを使う
- 仮想環境やプロセスを分ける

などの選択肢を比較します。

### パッケージング競合解決編

依存パッケージのバージョンCONFLICTだけでなく、
Pythonパッケージを作る・配る・インストールする段階の問題も扱います。

候補:

- wheelが使えずsdistからビルドされる
- build backend不足
- build dependency不足
- build isolation内だけ失敗する
- Pythonバージョン非対応
- OS / CPU向けの配布物がない
- `pyproject.toml` の `build-system` 設定ミス
- editable installでは動くが通常installでは壊れる
- package dataがwheelへ入っていない

正常な小さなパッケージを1か所ずつ壊し、
build / install時にどの層で失敗しているのかを切り分けます。

最後は必ずwheel等の配布物を作り、
新しい仮想環境へインストールして確認します。

### 依存関係がインストールされない問題解決編

`pip install` 自体は成功したのに、
実行すると必要な外部パッケージが見つからない問題を扱います。

典型例:

```text
pip install example-package
→ 成功

import example_package
→ ModuleNotFoundError
```

扱う候補:

- `pyproject.toml` のdependenciesへの宣言漏れ
- optional dependencies / extrasを入れていない
- environment markerによる条件付き依存
- dev依存とruntime依存の混同
- 別パッケージが偶然入れてくれる間接依存へ頼っている

開発環境では既に必要なものが入っていて気付かない問題を再現し、
**clean environmentで検証することの意味**まで扱います。

### 問題演習・ノック編

試験やコーディング課題に近い形式で、Pythonを自分で書く問題を多数用意します。

問題形式は一つの教材へ混ぜず、少なくとも次のように分けます。

- **穴埋めノック**: コードの一部を埋め、Pythonの構文や標準機能を反射的に取り出す
- **機能実装ノック**: 仕様を読み、関数や小さな機能全体を自分で実装する
- **標準入出力ノック**: AtCoder等に近い形式で、入力を読み、処理し、指定形式で出力する

どの形式も「難問を解く」ことより、**問題を見たときにPythonの書き方が頭に浮かぶ状態を作る**ことを重視します。

候補:

- 関数穴埋め
- 仕様だけを読んで関数を実装する
- 既存コードの未実装部分を完成させる
- AtCoder風の標準入力 / 標準出力問題
- テストを読んで実装を完成させる
- 境界値を含む問題

AtCoder等に近い問題形式は使えますが、
**実行時間の順位・最短コード・競技としての速さは目的にしません。**

問題文や仕様を読み、

> 自分で実装する
> → テストする
> → 失敗したケースを確認する
> → 修正する

という経験を増やすことを目的にします。

問題ページでは解答例を先に見せません。

この系列では、**正解は実装方法ではなく入出力で決まる**という考え方を基本にします。

同じ入力に対して仕様どおりの出力になるなら、内部の実装方法が違っていても正解として扱います。

そのため教材側が提示するコードは「正解」「模範解答」ではなく、**解答例**と呼びます。

解答例側では、

- 1つの実装例
- 別の書き方
- そのコードが何をしているか
- よくある間違い
- 境界値でなぜ失敗するか

を説明します。

必要な副作用やファイル出力などがある問題では、それらも入出力仕様として明示します。

上級編は応用編の「ゆっくり作る / 完成品から読む」という2系統へ無理に合わせず、
教材ごとに調査型・問題解決型など適した進め方を採用します。

- モデリング
- マテリアル
- アニメーション
- レンダリング
- Blender Python API
- 自動化
- アドオン作成

などは、Blender教材の中で扱います。

Pythonを知っていることは助けになりますが、

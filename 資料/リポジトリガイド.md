# Learning_language - リポジトリガイド

## このリポジトリについて

このリポジトリは、プログラミング言語を初めて学ぶ人のために、
**読みやすい解説と、コメント付きの小さなサンプルコード**をまとめることを目的としています。

特に、一般的な入門資料が少ない言語や、古い資料・断片的な資料しか見つからない言語についても、
「最初に何を書けばよいか」「どう実行するか」「そのコードが何をしているか」を追いやすい形で残します。

Python や JavaScript のように教材が豊富な言語も対象にできますが、
情報の少ない言語ほど、このリポジトリで扱う価値が高いと考えています。

## 最初に扱う言語

最初の教材は **Python** とします。

まず Python で教材の構成、説明量、コメントの書き方などの感触を確認し、
その形式を今後ほかの言語へ展開していきます。

## 基本構成

リポジトリ全体に関する説明は `資料/` に置きます。

実際の学習教材は `教材/` にまとめます。
各プログラミング言語はその配下で言語ごとのディレクトリに分け、
その中に説明用 Markdown とサンプルコードを配置します。

例:

```text
Learning_language/
├─ README.md
├─ 資料/
│  ├─ リポジトリガイド.md
│  └─ ライセンス方針.md
└─ 教材/
   ├─ 教材一覧.md
   ├─ コンピュータ基礎/
   │  ├─ コンピュータ基礎ガイド.md
   │  └─ ...
   └─ <言語名>/
      ├─ 初めに.md
      ├─ <教材系列>/
      │  ├─ 初めに.md
      │  ├─ 目次.md
      │  └─ 教材/
      │     └─ <章・サンプル・assets>
      └─ ...
```

リポジトリ制作・保守時のライセンス判断は、[ライセンス方針](./ライセンス方針.md) にまとめます。

正式な利用条件はリポジトリ直下の `LICENSE` を正本とし、制作ルールとは分離して管理します。

各言語では、学習項目を番号順に並べます。

番号付き教材フォルダの番号部分は **2桁ゼロ埋め** にします。たとえば `00_`、`01_`、`Pg01_`、`Tk03_`、`St01_` の形式です。本文の見出しや表示する章番号は `Pg1`、`Tk3` のままで構いません。

Pythonは、基礎編の2系列、応用編の2系列、上級編に分けます。各系列の直下は `初めに.md` と `目次.md` を入口とし、章・サンプル・素材は `教材/` 配下へ置きます。公開中の教材と準備中の系列は、[Pythonの入口](../教材/Python/初めに.md)で区別します。

読者向けの入口ファイルは `初めに.md` とします。リポジトリ全体の `README.md` や素材の出所・ライセンスを管理する `assets/README.md` は残します。

各言語の最初の項目 `0` では、まず **その言語がどのような言語なのか** を説明します。

その後の項目で環境構築へ進みます。Python では `0. Pythonとは？`、`1. 環境構築` という順番にします。

## 共通のコンピュータ基礎教材

プログラミング言語とは別に、`教材/コンピュータ基礎/` に
**コンピュータ基本用語と OS 操作の共通教材**を置きます。

ここでは、ファイル・ディレクトリ・パス・ターミナル・環境変数・権限・プロセス・ネットワークなど、
言語に依存しない知識を扱います。

`教材/コンピュータ基礎/` は、各言語の教材を読むための必須の前提資料にはしません。

各言語の環境構築やサンプルコードを進めるために必要な操作や用語は、
**可能な限りその言語側の教材にも直接書きます。**

学習者が Python や C などを学びたいのに、
その途中で別の操作ガイドを何章も読まなければ先へ進めない構成は避けます。

`教材/コンピュータ基礎/` は主に、

- 仕組みをより詳しく知りたい場合
- OS 操作そのものを体系的に学びたい場合
- 言語に依存しない知識を後から確認したい場合
- トラブル時に背景知識まで含めて確認したい場合

に使う補助資料とします。

そのため、各言語の教材と `教材/コンピュータ基礎/` では、
必要に応じて説明内容が一部重複しても構いません。

**学習の流れを止めないことを、重複を避けることより優先します。**

最終的には Windows / macOS / Linux の基本操作を、
プログラミング学習で必要になる範囲で一通り扱うことを目標とします。


## 変更の運用

このリポジトリでは、基本的に **Pull Request（PR）を使って変更します。**

変更作業中に `main` の内容が途中状態になり、
教材が読みにくくなったりリンクが一時的に壊れたりすることを避けるためです。

基本の流れは次のとおりです。

1. `main` から作業用ブランチを作る
2. 作業用ブランチで変更する
3. 変更がまとまったら PR を作る
4. 内容を確認する
5. 問題がなければ `main` にマージする

このリポジトリでは、PR を厳しく選別すること自体が目的ではありません。

**変更途中の状態を `main` に出さず、常に読める状態を保つこと**を主な目的とします。

小さな修正でも、複数ファイルの移動やリンク変更を伴う場合は特に PR を使います。

作業を選ぶ前に、[Issueの優先度運用](./Issue優先度運用.md)に従って最新のopen Issueと関連PRを確認します。優先度ラベルはP0〜P8を1つ付け、P0は緊急対応専用とします。


## 教材の基本方針

教材は、初学者が次の順序で理解できることを重視します。

1. その言語がどのような言語なのかを知る
2. 実行環境を用意する
3. 最小のプログラムを動かす
4. サンプルコードをコメントと解説を読みながら理解する
5. 変数、条件分岐、繰り返し、関数などの基本機能を学ぶ
6. その言語特有の考え方や機能を学ぶ

## 困りごとから章へつなぐ

章や新しい機能の導入は、読者がその機能を欲しくなる具体的な場面から書きます。今後追加する他言語の教材にも適用します。

1. **困った場面**：誰が何をしようとして、どこで困るかを示す。「何がないと何が困るか」が分かる例にする。
2. **欲しい結果**：「名前を変えるたびにコードを書き換えたくない」「次に何を入力すればいいか知りたい」など、困りごとがどう解消してほしいかを書く。
3. **その章の題材**：実際のサンプルで何を試せるかへつなぐ。機能名や仕組みの説明は、そのあとに必要な順で置く。

「この章では例外処理を学びます」「異常終了しない小さなプログラムです」だけでは、使う理由が伝わりません。たとえば「数字の欄へ『ねこ』と入力したら、長いエラー表示で終わって何を直すか分からない。何を入れ直せばいいか案内が欲しい。そのために、入力の問題を扱って案内を表示する」とつなげます。

困りごとを短く表すツッコミや口語表現は、読者が場面を思い浮かべる助けになります。たとえば「誰もおらんやん！主人公どこ行った！！！」は、空のゲーム画面に自機が欲しい理由を伝えています。口語だからという理由で削除したり、機能の説明文へ丸めたりしません。前後には、その場面と欲しい結果を具体的に書きます。新しい表現を足すときは、無理に方言を作らず、自然な口語を使います。

導入で、まだ試していない仕組みを「本質は〜」「〜するだけ」と先に総括しません。「役に立つ」「便利」だけで済ませず、何を手で書かずに済むか、何が残るか、どの操作ができるかを示します。

サンプルにない機能を到達目標にしません。案内を表示して終了する例なら、その実行中に入力をやり直せるとは書きません。練習のための表示や挨拶は、どの困りごとや画面操作を確かめる例なのか説明します。未公開の教材は、できることと準備中のことを区別します。

同じ問題が複数のページにある場合は、章題直後だけでなく、途中の新しい機能を導入する節も確認し、監査Issueへまとめて対応します。

## 読者の操作とプログラムの動作

教材本文では、誰が何をするのかを分けて書きます。今後追加する他言語の教材にも適用します。

| 書く内容 | 書き方 | 例 |
| --- | --- | --- |
| 読者がする操作 | 「〜してください」で指示する | 「ターミナルへ `python hello_world.py` と入力し、Enterキーを押してください。」 |
| Pythonやプログラムがする処理 | 主語を明記し、動作を説明する | 「Pythonは入力された文字列を整数へ変換します。」 |
| 画面に出る結果 | 表示するものを主語にするか、表示される結果を書く | 「プログラムが `Hello World!` と表示します。」 |
| 章の題材 | どんなプログラムやコードなのかを書く | 「この章の題材は、入力した2つの数字を足すプログラムです。」 |

読者への指示に「保存します」「入力します」「押します」という宣言を使いません。入力してはいけない部分は「入力しないでください」と書きます。

操作の文と結果の文は分けます。たとえば「名前を入力し、Enterキーを押してください。そのあと、プログラムが入力した名前で挨拶を表示します。」と書きます。

コードを読む節では、既に掲載した処理を「追加してください」と指示しません。「このコードは、弾を一覧に追加する処理です。」のように説明します。変更を求める節では、編集するファイルと箇所を示して「変更してください」と書きます。

コードを挟む場合も、説明の文を途中で切りません。「で実行します」「と表示します」だけをコードの後ろに置かず、何が何を実行するか、何が表示されるかを一文で書きます。

コメントはコードの処理の説明です。読者への操作指示とは分け、本文と同じ主語・処理の関係にします。

同じ問題が複数のページにある場合は、該当ページを横断して修正します。同じ指摘をページごとのIssueに分割せず、監査Issueに対象と修正結果をまとめます。

## ツール・画面の開き方

ツールや機能を使わせる箇所には、名前だけでなく、開くために押す場所や検索する文字を書きます。別のページで説明済みでも、その場で操作できる手順を置きます。今後追加する他言語の教材にも適用します。

- OSのアプリは、検索欄やアプリ一覧を開く場所、入力する名前、選ぶ項目を書く
- VS Codeの機能は、メニュー名やアイコンの位置、選ぶ項目を書く
- コマンドパレットは、開くキー操作、表示される入力欄、入力する文字、一覧から選ぶ項目を書く
- 「開き直す」ときは、閉じ方と再び開く操作も書く

## コマンドの入力手順

教材でコマンドを実際に入力させる箇所には、毎回、次の操作まで直接書きます。

1. ターミナルをどのメニューから開くか
2. 開いたターミナルへ何を入力するか
3. 入力後に Enter キーを押すこと

前のページや節で説明済みでも省略しません。複数行のコマンドは、1行入力するたびに Enter キーを押すことを明記します。

フォルダの移動や仮想環境の有効化に続く操作は、同じターミナルで行うことも書きます。VS Code では **表示（View）→ ターミナル（Terminal）** からそのターミナルを表示し、途中で新しいターミナルを作る案内に置き換えないようにします。

プログラムを動かす前に保存先への移動が必要な場合は、その入力と Enter キーの操作も書きます。VS Code をまだインストールしていない場面では、OS側のターミナルの開き方を使います。

「コピーしたパス」を使う箇所には、対象ファイルの名前、開く保存先のフォルダ、パスをコピーする画面と欄を直接書きます。コピーするキー操作と、コマンドのどの部分へ貼り付けるのかも書きます。前の節を読んだことを前提にして省略しません。

コード、入力するコマンド、表示される結果を区別します。実行不要の例や説明用の一覧には、実際に入力する手順を付けません。

## サンプルコード

実ファイルとMarkdownに掲載する実行コードの両方で、**原則としてすべての処理に日本語コメントを付けます**。その章で新しく追加した処理だけでなく、前章から引き継いだ処理も対象です。今後追加する他言語の教材にも同じ基準を適用します。

### コードコメント

コメントは、**そのコードに書いてある処理を日本語でそのまま読める形**にします。

- 実際の変数名を使い、代入では「何をどの変数へ入れるか」を書く
- 条件・繰り返し・呼び出し・return・描画なども、そのコードの具体的な処理を書く
- 物理的な1行ごとではなく、1つの処理・1つの意味のまとまりごとに付ける。複数行の呼び出しには、呼び出し全体を説明するコメントを付ける
- 一般説明コメントを添えてもよいが、それだけで具体的な処理コメントを置き換えない
- 同じサンプルを実ファイルとMarkdownに載せる場合は、コメントも一致させる
- 機能を少しずつ追加する系列では、最初の章から順に整える。前章とコード・役割が同じ箇所は、コメントの文言もそのまま引き継ぐ
- 似た処理が続く箇所には「足し算」などの短い見出しコメントも付ける。見出しの下には具体的な処理コメントを書く

例:

```python
# number1 に2を入れる
number1 = 2

# number2 に3を入れる
number2 = 3

# answer に number1 と number2 を足した値を入れる
answer = number1 + number2

# 「答えは」と answer と「です」を表示する
print("答えは", answer, "です")
```

### Markdown本文

本文では、コードコメントに対応する処理を説明したうえで、次の内容を補います。

- なぜその処理が必要か
- 新しく登場した用語・構文・仕様の意味
- 英語の変数名や関数名の意味
- 初期値や数値を選んだ理由、引数の順番や単位
- 値を変えると結果がどう変わるか
- 操作手順や、つまずきやすい点

正式なコメント方針は [Issue #103](https://github.com/tomiya7688/Learning_language/issues/103)、名前・値の本文解説は [#104](https://github.com/tomiya7688/Learning_language/issues/104)・[#105](https://github.com/tomiya7688/Learning_language/issues/105)・[#106](https://github.com/tomiya7688/Learning_language/issues/106)、掲載コードのコメント確認は [#396](https://github.com/tomiya7688/Learning_language/issues/396)で管理します。

一つのサンプルに多くの概念を詰め込みすぎず、
できるだけ小さく、実際に動かして確認できるコードを優先します。

## Markdown の方針

解説は GitHub 上でそのまま読みやすい Markdown とします。

必要に応じて以下を含めます。

- 短い説明
- コード例
- 実行方法
- 実行結果
- 補足
- 関連する次の学習項目

# 1. 開発でよく見るファイルと名前

プログラミングを始めて GitHub や開発用フォルダを開くと、
最初から多くのファイルやフォルダが並んでいることがあります。

初学者には、それだけで「難しそうなもの」に見えます。

しかし実際には、それぞれに役割があります。

まずは、よく見る名前と関係だけ知っておきましょう。

---

## まず全体像

たとえば、次のような構成があるとします。

```text
電卓アプリ/
├─ README.md
├─ LICENSE
├─ src/
│  └─ main.py
├─ tests/
│  └─ test_main.py
└─ config.json
```

これは、1つの **プロジェクト** の中に、

- 説明書
- ライセンス
- ソースコード
- テスト
- 設定ファイル

などが入っている例です。

Git でこのプロジェクトを管理すると、
その管理単位を **リポジトリ** と呼びます。

---

## ファイル

**ファイル** は、データを保存する単位です。

例:

```text
main.py
README.md
LICENSE
config.json
```

Python のコード、説明文、設定なども、
すべてファイルとして保存されます。

---

## フォルダ

**フォルダ** は、複数のファイルや別のフォルダをまとめる入れ物です。

例:

```text
src/
tests/
images/
```

技術資料では **ディレクトリ** と呼ばれることもあります。

最初は、

> フォルダ = ディレクトリ

と考えて問題ありません。

---

## プロジェクト

**プロジェクト** は、ある目的のためにまとめられたファイルやフォルダ全体を指すことが多い言葉です。

たとえば、

- 電卓アプリ
- Webサイト
- ゲーム
- 自動化ツール

など、1つの成果物を作るための一式をプロジェクトと呼びます。

厳密な決まりがある言葉ではなく、
文脈によって少し広い意味で使われることもあります。

---

## リポジトリ

**リポジトリ** は、Git などのバージョン管理システムで管理されているファイル一式です。

GitHub で1つのページとして表示されている単位も、基本的には1つのリポジトリです。

たとえばこの教材自体も、

```text
Learning_language
```

という1つのリポジトリです。

### プロジェクトとリポジトリは同じ？

同じ意味のように使われることも多いですが、少し違います。

- **プロジェクト**: 作っているもの・作業全体
- **リポジトリ**: Git で管理している単位

小さな開発では、

> 1プロジェクト = 1リポジトリ

になることが多いため、ほぼ同じ意味に見えます。

大きなシステムでは、1つのプロジェクトを複数のリポジトリに分けることもあります。

---

## README

`README` は、

> **まず読んでください**

という意味で置かれる説明ファイルです。

GitHub では、

```text
README.md
```

という名前が非常によく使われます。

よく書かれている内容は、

- これは何のプロジェクトか
- 何ができるか
- インストール方法
- 使い方
- 必要な環境
- 注意事項

などです。

GitHub は `README.md` を見つけると、
リポジトリやフォルダの説明として自動的に表示します。

### なぜこの教材では README.md をあまり使わないの？

`README.md` は開発では一般的な慣例ですが、
初学者にとっては名前だけでは内容が分かりにくいためです。

そのため、この教材ではリポジトリの一番上を除いて、

```text
Python学習ガイド.md
環境構築ガイド.md
基本用語.md
```

のように、できるだけ中身が分かる名前を使っています。

ただし、他のプロジェクトでは `README.md` が非常によく使われるので、
意味は知っておく必要があります。

---

## LICENSE

`LICENSE` は、そのソフトウェアや資料を

- 使ってよいか
- 改変してよいか
- 再配布してよいか
- 商用利用してよいか

などを示すためのファイルです。

代表的なライセンスには、

- MIT License
- Apache License 2.0
- GPL

などがあります。

コードが公開されているからといって、
必ず自由に何でもしてよいとは限りません。

公開されているコードを利用するときは、
`LICENSE` の内容を確認する習慣をつけましょう。

---

## ソースコード

人が書いたプログラムの元となるコードを **ソースコード** と呼びます。

Python なら、

```text
main.py
app.py
game.py
```

などがソースコードです。

`src` というフォルダにまとめられていることもあります。

`src` は **source** の略です。

---

## tests

```text
tests/
```

というフォルダには、プログラムが正しく動くか確認するための **テストコード** が置かれることがあります。

最初は中身を理解できなくても問題ありません。

> 本体とは別に、動作確認用のコードが入っている

くらいに考えてください。

---

## docs

```text
docs/
```

は **documents / documentation** などを意味し、
詳しい説明書や仕様書を置くフォルダとしてよく使われます。

この教材では日本語を優先しているため、

```text
資料/
```

という名前を使っています。

---

## config

`config` は **configuration（設定）** の略です。

たとえば、

```text
config.json
config.yaml
settings.json
```

のような名前で、プログラムの設定を保存することがあります。

---

## .gitignore

Git を使うプロジェクトでは、

```text
.gitignore
```

というファイルをよく見かけます。

これは、

> Git で管理しないファイルやフォルダを指定する

ためのファイルです。

たとえば、

- 一時ファイル
- キャッシュ
- 仮想環境
- ビルド結果

などを除外するために使います。

名前の先頭が `.` なので、
OS の設定によっては隠しファイルとして扱われます。

---

## 拡張子も手がかりになる

ファイル名の最後を見ると、
何のファイルかある程度分かります。

例:

```text
main.py       → Python
README.md     → Markdown
config.json   → JSON
style.css     → CSS
index.html    → HTML
```

知らないファイルがあったら、
まず **ファイル名と拡張子を見る** と役割を推測しやすくなります。

---

## 最初から全部理解する必要はない

開発用のリポジトリを開くと、多くのファイルが並んでいることがあります。

しかし最初から全部読む必要はありません。

まずは、

1. README やガイドを見る
2. 何を作るプロジェクトか確認する
3. 実行方法を探す
4. ソースコードがどこにあるか確認する

くらいで十分です。

ファイルが多いことと、プログラム自体が難しいことは別です。

**「何のためのファイルか分からない」状態を1つずつ減らすだけで、リポジトリはかなり読みやすくなります。**
